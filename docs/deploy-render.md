# انتشار Fika روی Render

## معماری
- یک سرویس Node.js (Web Service): `server.js` هم API و هم فایل‌های `public/` را سرو می‌کند. فرانت جدا ندارد، پس CORS و Rewrite لازم نیست (مسیریاب با `#/` کار می‌کند).
- بدون وابستگی npm. نیازی به Docker نیست.
- دیتابیس یک فایل JSON است (`DB_FILE`). همراهش کلید رمز (یا `DATA_KEY`)، پشتیبان‌های رمزشده و `security.log` در همان پوشه ذخیره می‌شوند.

## هشدار مهم: داده‌ها و پلن
فایل‌سیستم Render موقت است. با هر Deploy، Restart و (در پلن رایگان) هر بار خواب رفتن سرویس، همه چیز پاک می‌شود. فقط پوشهٔ Disk پایدار می‌ماند و Disk فقط برای سرویس پولی هست.

| حالت | داده‌ها | مناسب برای |
|---|---|---|
| `plan: free` بدون Disk | با هر خواب/Restart پاک می‌شود، بعد از ۱۵ دقیقه بی‌ترافیک خواب می‌رود | فقط دمو |
| پلن پولی + Disk در `/var/data` (تنظیم پیش‌فرض `render.yaml`) | ماندگار | کافهٔ واقعی |

با Disk سرویس فقط یک نمونه می‌تواند باشد (نباید Scale کنی) و هر Deploy چند ثانیه قطعی دارد.

## مراحل
1. در GitHub یک Repository بساز (ترجیحاً **Private**) و پروژه را Push کن (دستورها در README).
2. در Render: **New → Blueprint** → Repository را انتخاب کن. Render فایل `render.yaml` را می‌خواند.
3. هنگام ساخت از تو `PUBLIC_URL` را می‌خواهد. هنوز آدرس نهایی را نمی‌دانی؛ هر مقدار موقت بگذار و بعد از Deploy اصلاحش کن (مرحلهٔ ۶).
4. Deploy را بزن و در **Logs** منتظر `Fika running on ...` بمان.
5. آدرس `https://<نام-سرویس>.onrender.com` را باز کن.
6. در **Environment**، `PUBLIC_URL` را روی همان آدرس (یا دامنهٔ خودت) بگذار و ذخیره کن.
7. **DATA_KEY** را از Environment کپی کن و جایی امن نگه دار (مثلاً مدیر رمز). بدون آن پشتیبان‌ها باز نمی‌شوند.

## ساخت مالک اولیه
روش ۱ (پیشنهادی): `https://<آدرس>/admin.html` را باز کن. چون از اینترنت می‌آیی «کد راه‌اندازی» لازم است. آن را در Render → Logs پیدا کن (خطی که با `Setup code` شروع می‌شود). نام، ایمیل و رمز **۱۲ حرف به بالا و غیرآسان** بده. بعد از ورود، ۲FA را فعال کن (اجباری است) و ۸ کد بازیابی را ذخیره کن.

روش ۲: در Environment مقدارهای `OWNER_EMAIL` و `OWNER_PASSWORD` را بگذار و Deploy کن. بعد از اولین ورود موفق `OWNER_PASSWORD` را حذف کن.

## متغیرهای محیطی
| نام | مقدار | توضیح |
|---|---|---|
| `NODE_VERSION` | `22` | نسخهٔ Node |
| `COOKIE_SECURE` | `1` | کوکی امن + حالت سخت‌گیر کارکنان (رمز ۱۲+ و ۲FA اجباری) |
| `TRUST_PROXY` | `1` | تعداد پروکسی‌های جلوی برنامه، برای IP واقعی. پایین را ببین |
| `DB_FILE` | `/var/data/db.json` | باید زیر مسیر Disk باشد |
| `DATA_KEY` | خودکار | کلید رمزنگاری، حتماً نسخه‌برداری شود |
| `PUBLIC_URL` | آدرس سایت | لینک بازیابی رمز |
| `PORT` | خودکار | Render خودش می‌گذارد |

## IP واقعی کاربر (TRUST_PROXY)
محدودیت‌ها (ورود، سفارش، …) بر اساس IP هستند. اگر عدد `TRUST_PROXY` درست نباشد، یا همهٔ کاربرها یک IP مشترک می‌شوند یا IP قابل جعل می‌شود. من نتوانستم رفتار هدر Render را از اینجا تأیید کنم، پس بعد از Deploy این‌طور بررسی کن:
1. مالک را بساز. در Logs خطی مثل `[security] setup {"uid":...,"ip":"..."}` می‌آید.
2. اگر `ip` برابر IP عمومی خودت است (در سایت‌هایی مثل whatismyip ببین): همان `1` درست است.
3. اگر IP دیگری بود (مثلاً Render/Cloudflare): `TRUST_PROXY=2` بگذار و دوباره مالک جدید یا یک رویداد دیگر بساز تا دوباره خط لاگ را ببینی. فقط عددی را نگه دار که IP خودت را نشان می‌دهد.

## پشتیبان و بازیابی
هر ۶ ساعت بررسی و روزی یک پشتیبان رمزشده در `/var/data/backups/` ساخته می‌شود (۱۴ تای آخر). این‌ها روی همان Disk هستند، پس برای خرابی Disk کافی نیستند. هر چند وقت یک بار یک نسخه را بیرون بگیر (Render → Shell یا Disk Snapshots) و با `node tools/restore-backup.js فایل.enc خروجی.json` (با همان `DATA_KEY`) بازگردانی کن.

## عیب‌یابی
| نشانه | علت محتمل |
|---|---|
| Deploy در Health Check رد می‌شود | سرویس بالا نیامده؛ Logs را ببین. مسیر `/healthz` باید `ok` بدهد |
| «حساب دسترسی مدیریتی ندارد» | با حساب مشتری وارد شده‌ای؛ مالک را با روش بالا بساز |
| بعد از هر Deploy همه چیز پاک است | Disk وصل نیست یا `DB_FILE` زیر `/var/data` نیست |
| ورود کارکنان رد می‌شود | حالت سخت‌گیر است: رمز ۱۲+ و ۲FA |
| بعد از ورود پروفایل باز نمی‌شود | سایت باید با `https://` باز شود و `COOKIE_SECURE=1` باشد |
| 502 پراکنده | باید با `keepAliveTimeout` برطرف شده باشد؛ Logs را ببین |
